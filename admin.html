Speaker label

The two labels down the left of the transcript. Either can be a variable instead of a fixed word: {name} — the word you say to reach whichever assistant is answering, so renaming that renames this. Already what the greeting and farewell fields use. {assistant} — what answered, which is its own field on each endpoint. This is the default, and with more than one endpoint it is the only label that can be right: a fixed word attributes every answer to the same name. Each line keeps the name of whoever gave it, so switching endpoints mid-conversation does not rewrite what is already on screen. {display} — the name of the device this is being viewed at. Put it in the person and every device attributes the transcript to itself, with no setting per device. It resolves to the first of these that exists: the name you gave that row under ACCESS, then ?display= from its URL, then the first thing typed on its request form. So a laptop you approved as Sarah laptop labels her lines with that, and a wall screen named Kitchen labels its own. A person's name as distinct from the device they are at — the same name following somebody from laptop to phone — needs an identity they carry, and does not exist yet. Mix them with ordinary text — {display} shift lead is fine. A variable that resolves to nothing falls back to the default, and one that is not recognised is left standing so a typo is visible rather than silent.

Wake word

Whether a name is needed at all, and how long one lasts. The words themselves live on the routes, in AI — with several routes the word is what picks between them, so it belongs to the thing it picks.
The word that reaches an endpoint using this profile, the spellings a transcriber actually returns for it, and how close a match has to be. EXACT is for a profile whose endpoint DOES things rather than answers — the same false-positive rate costs a few tokens on one and actuates hardware on the other.
The fallback for every route that has no greeting of its own. Several lines so a display somebody talks to all day does not repeat itself; {name} is the word that was said to reach whoever answered.

Speech in (mic, STT)

Everything here runs on this server — no audio leaves the box for transcription, whichever model is chosen. transcription model is grouped: the .en models are English-only, smaller and better at English than the multilingual model of the same size; picking one from every language is the only thing that makes this transcribe anything else. Sizes run from ~40MB to ~1.6GB and each option says what it costs, so the list assumes nothing about the machine you are running on. A bigger box wants large-v3-turbo; a modest one wants distil-small.en or the default small.en. A model not already on disk is downloaded the first time somebody speaks after you pick it — inside that request, up to 1.6GB, from a machine that may have no route out. Switch when nobody is waiting at a display, then say something to it yourself to pay for the download. The smaller the model, the more often a wake word is mis-heard — and an assistant set to THE EXACT WORD refuses a near-miss outright, where a CLOSE ENOUGH one forgives it. If you want a fast model on a strict assistant, press LEARN HOW I SAY IT on that assistant and it will accept the spellings this model actually returns. CLEAN filters the input for recognition; RAW leaves it alone, so the figure moves more and transcription is slightly worse. CALIBRATE measures the room rather than asking you to guess at the gate.

IP Address

Which addresses the server answers on. Binding one address rather than every interface is worth doing on its own account: a laptop that later joins another network does not follow you onto it. This machine only needs no certificate — browsers already treat http://localhost as a secure origin, so the microphone works unprompted and nothing crosses a network. Start it, open localhost, talk to it.

Ports

The port this page answers on, and only this one. What the app answers on is a network profile — PROFILES ▸ NETWORK — because a deployment can want several, and which endpoints each carries is a question about the app rather than about the portal. This one stays here on purpose: it is the way back in when what is over there is wrong.
1024–65535, and not a port a network profile is using. Below 1024 needs root, and the server runs as an ordinary user.

Maintenance

What keeps a screen nobody touches working. Every display checks in on the interval below. That check-in is what keeps LAST SEEN honest in DEVICES, what lets RELOAD there reach a screen, and what lets a screen notice on its own that the server has come back — without it, an outage would end and the screen would stay broken until somebody walked up and spoke to it. A display that has run out of attempts shows a line high on the screen, which clears itself when the server answers again. A kiosk also says it aloud, once — it has no transcript and nobody sitting at it. Nothing else speaks: a screen with somebody in front of it fails at the moment they actually use it, rather than making them wait out the retries. These take effect at each display's next check-in. No restart.
2–300, 1–10 and 1–60. Three attempts is right for a server being restarted and wrong for a cable somebody pulled out, which is why it is a field rather than a constant. Anything outside a range is nudged back into it rather than refused.
Every display reloads itself once a night, because a tab that never reloads accumulates. Off by default. Read off each device's own clock, not this server's, for the same reason a screensaver's dark hours are: a screen's night is the night outside it. And deferred while somebody is talking to the screen or typing into it — a reload that lands between a question and its answer looks like a crash to whoever asked. Spread it if the building has more than a handful of screens: twelve tablets reconnecting in the same second is a load this server did not previously have. Each screen takes its own fixed slot inside the window, so the spread stays put instead of re-shuffling every night.
The server itself, once a day. Off by default. Read off this machine's clock, not a device's — this one is about one server rather than twelve screens. It hands over rather than stopping: at the appointed minute the server launches serve.sh restart in a session of its own and lets that script kill it and start a fresh process. Nothing supervises this server, so a setting that merely stopped it would be a setting that ended the service at three in the morning. The one risk worth knowing. If the new process cannot bind — something else took the port while it was down — nothing catches that, and the server stays down until somebody looks. It is logged to restart.log, which survives the handover where server.log does not. It waits for the server to fall quiet: no question, transcription or spoken reply for a minute. If it never falls quiet it gives up after an hour and leaves it for tomorrow, rather than cutting somebody off mid-sentence. Every display sees this as a short outage and reloads itself when the server answers again — so if you set this, you rarely also need the nightly refresh above.

Security

AI Requires Permission

YES — they get the request form instead of the transcript and composer, and reach nothing until you decide. NO — they open the page and use the default endpoint straight away. Restricted endpoints still need a code you issued. Only settable while an endpoint open to any display is the default, or NO would mean access to nothing.
A granted request runs out and the person asks again — one press for them, because what they told you is kept. Displays you issued a code for never expire, whatever this says: a screen on a wall going dark on a timer is not a security property, it is an outage. When more than the waiting limit are queued, the oldest one waiting is dropped to make room — so set it high enough that a real request cannot be pushed out by noise.

Enrolment codes

How long a code is worth anything for after you press GET A CODE. Ten minutes by default, because the usual case is somebody walking across a building with six characters in their head — and the clock beside each one under ENROLLMENTS ▸ DEVICE is counting this down. Zero switches the clock off, and that is a real answer rather than a way of being careless: a code is one use, and the row it enrols was approved the moment you created it. A deployment that mints codes on Friday and hangs the screens on Monday is not less safe for it — what a code can do is become one screen you already decided to have. The clock applies from the moment a code is issued, so changing this does not extend one already out there. REISSUE gives that row a fresh one on the new setting.

Sign in

What it takes to reach this configuration page. Nothing is for a machine only you can reach, where the network is already the boundary and accounts add nothing — and it is what makes a personal install possible without fishing a generated password out of a log. Accounts & roles is the default, because the safe default is the one that assumes it can be reached. A single PIN — one number for the whole display, no account management — is the middle rung and is not built yet. It is the PIN machinery from identity pointed at a display rather than a person, so it lands with that.

Sessions

Idle minutes before an admin has to sign in again. Activity pushes the deadline out; the panel checks every 45 seconds and returns you to the sign-in as soon as it lapses. Short by default — this session configures what everyone else is looking at. 5 to 480. Full reasoning in DOCUMENTATION → App settings & accounts.
Groups
A group of people holds those who asked for access and were approved. A group of devices holds the screens you created and sent a code to. They are separate populations answering separate questions — the physics department and the screens in the east wing — so a group holds one or the other, and its kind cannot be changed once it exists. Name a group under an endpoint's who may use it and everyone in it may reach that endpoint. Grants add up: a group never takes away a grant made to one device on its own, and somebody whose access has run out is still refused whatever group they are in. Deleting a group removes it from every endpoint that named it. The devices and people in it are untouched — a group is a way of referring to them, not a thing they belong to.
Appearance profiles
The APPEARANCE tab is one document for everybody, and that is right for almost all of it — tune the bloom once and every screen in the building gets it. It is wrong for exactly four values. A screen in a hallway is read from three metres. A laptop is read from fifty centimetres. One type size cannot be right for both, and neither can one layout: a wall wants the figure filling the frame, a desk wants room for the transcript beside it. So type size, palette, layout and the figure become a profile a device names, and everything else stays shared. A device that names none of these shows what the APPEARANCE tab says, which is what every display did before this existed. Deleting a profile puts every device that named it back to that, rather than to nothing. PREVIEW lays a profile over the preview on the right without saving it, and follows the controls as you change them. Pressing STOP — or touching anything on APPEARANCE, GEOMETRY or SPEECH — puts the shared document back. Type size tops out at LARGEST, which is the range the APPEARANCE tab offers. If that turns out not to be enough on a real wall, the range is the thing to change, not this.
Geometry profiles
A snapshot of the GEOMETRY tab under a name. Set the rotation, the spectrum and the noise floor up there, watch the preview, then ADD A PROFILE to capture exactly what you are looking at. LOAD puts a profile back into the tab so you can see it and change it; UPDATE replaces it with whatever the tab says now. Loading does not publish anything — the tab is dirty afterwards exactly as if you had moved the controls by hand.
Speech profiles
A snapshot of the SPEECH tab under a name — the voice, the transcription model, the wake and sleep words, the microphone handling. A hallway that has to hear over a corridor and a quiet office want different microphone settings and the same everything else. LOAD puts a profile back into the tab; UPDATE replaces it with what the tab says now.
Model profiles
Where the connection lives: which provider, which base URL, which model, and the key for it. An endpoint on the AI tab picks one. The key never comes back to this page. It is stored on the server and the panel is told only whether there is one — so a profile shows key stored rather than the key, and saving without typing one keeps what is already there. DEMO needs nothing else: the display answers from built-in replies, which is how you tell a fault in the interface from a fault in whatever it is pointed at.
Network profiles
A port of this server's own, answering as one endpoint and nothing else. An endpoint on the AI tab picks one; an endpoint that picks none is reached on the shared display port, by its wake word, as they all were before this existed. What a browser opening that port gets is the ordinary interface built from that endpoint's own settings — its speech profile, its greeting, its voice — with no other endpoint offered and nothing to address by name. The port is the grant turns off the request form on that port alone: a device that can reach it uses the endpoint straight away. That is a statement about your network, not about this server — it is right when the port is on a VLAN only the intended devices are on, and wrong the moment it is not. TLS is the same certificate the display port uses, because the microphone needs a secure context and a second certificate for the same machine would be one more thing to renew. Ports are bound when the server starts. Adding a profile, changing a port or pointing a different endpoint at one takes a restart, exactly as the ports on ADMIN SETTINGS do — a listening socket is not something to open and close under a mouse.
Screensaver profiles
A screen showing the same bright figure in the same place for years keeps a ghost of it permanently. A profile is the answer to that, and it is still the product: the same face, every appearance setting still applied, scaled down and drifting. Set them here, pick them on a device. A hallway, a bedroom, a shop floor — that is a handful of kinds of place, not one setting per screen. Change night once and every screen using it changes together; the alternative is twelve rows quietly drifting out of step with no way to see which had. Idle seconds is how long with nobody speaking to it and nobody touching it. 0 never starts, which is how you park a profile without deleting it and unpicking every device that names it. Shrinks to is what makes the drift possible at all: drawn edge to edge there is nowhere to go, and moving it would only clip the sides. The travel is exactly the margin the shrink buys, so nothing is ever cut off. Dims by does more against a ghost than the movement does, and is independently what a hallway should do at two in the morning. It stops short of switching the screen off — you can still see across a room that it is working. PREVIEW tries a profile in the preview on the right without saving it. Nobody picks a scale and a dim by reading two numbers. It ends on the wake word or on a touch, easing back to the middle rather than snapping, and it never starts while an answer is being thought about or spoken. The transcript, the composer and the status line hide while it drifts, and come back the instant the screen is touched. Dark from / until is a different question from the idle delay, and the reason it exists: idle asks whether anybody has been here recently, and only a clock keeps a hallway dark after somebody walks past it at three in the morning. Set the two hours the same and there is no dark window. A start later than an end wraps midnight, which is the ordinary case — 22:00 to 07:00 is what you mean. The two dims never add up. Whichever is darker at that moment wins, so a screen already drifting at night does not go past black. The hours are read off the device's own clock, not this server's. A building with screens in two time zones wants each of them dark at its own two in the morning. Deleting a profile clears it from every device that named it, the same way deleting a display clears it from every endpoint. Nothing keeps drifting to numbers that are no longer here. On a device, in DEVICES, tick Kiosk mode and pick which of these profiles it is. Untick it and the screen goes back to being an ordinary page; what you chose is kept, so putting it back up restores it. A wall is voice only and speak only the moment you tick it. No text box — voice only arrives already ticked, and you untick it for the case that wants a transcript. And no keyboard: push-to-talk holds the SPACE bar, which a tablet on a wall does not have, so a wall always listens and the SPACE button is removed from that screen. That is also what makes the wake word real, because the gate is inactive in push-to-talk. TEXT and SPACE are removed rather than left there refusing. TALK and AUDIO stay — a browser will not open a microphone unless somebody asks it to, so TALK is pressed once when the screen is commissioned. It goes full screen on the first touch. An address bar and a tab strip across the top of a hallway screen is a browser that happens to be running a display. No page can remove that chrome, but it can ask to be shown full screen, and a browser grants that off a gesture — which is why a touch and not a load. Press Escape and it stays out for a minute, because whoever left full screen is nearly always the person installing the screen. It says what to say to it. A wall carries one dim line low in the frame — say “kitchen”, in whatever the wake words are — for the person walking past who has no way of knowing it listens. Never on a browser tab, and not while somebody is talking to it. While the screensaver drifts it is drawn into the picture and travels with it, because taking it away would lose it for exactly the person it is for. It keeps the screen awake. A tablet that has let its backlight go out cannot be walked up to and spoken to: the microphone is behind a page nobody can see. Untick it on a television, or on a device whose operating system is already set never to sleep, where holding the lock gains nothing. When a device takes a change. Every display checks in on the interval under APP SETTINGS ▸ MAINTENANCE, and reloads itself when something it draws from changes — so an appearance or a profile edited here reaches the wall without anybody walking to it. Never while somebody is talking to the screen or typing into it: it waits until they have finished. RELOAD on a device's row in DEVICES asks one directly.
Display profiles
A kiosk is a screen people walk up to, that nobody has open and nobody is sitting at — a wall, a stand, a reception counter, a tabletop. The mounting was never what any of this followed from: what it follows from is that nobody owns the session and nobody has a keyboard. Build them here, pick one on a device. A hallway, a reception desk, a shop floor — a handful of kinds of place, not one setting per screen. Change what a hallway does once and every hallway screen changes with it. Voice only takes away the transcript and the composer, and it outranks what the viewer chose: a hallway is not a workstation, and a screen of scrolling text in one is neither useful nor discreet. Full screen is asked for on the first touch. Turn it off where somebody also browses on that machine, or where the operating system already hides the chrome. The prompt line is one dim line low in the frame telling a passer-by this listens. Leave the text empty and it writes itself from the wake words the screen actually answers to — which stays right when you rename one. Type something only where the generated line is not the point. The default is what a device gets when it names no profile, and you choose which one that is. A screen hung on a wall and never configured behaves like the rest of the building rather than like nothing.

The request form

Up to five fields, and they are yours — this server has no opinion about what a request should ask. Somebody running a campus wants a name and a department; somebody running a house wants none of it. Tick message on one field to make it a box big enough for a reason, and mark the ones that must be answered. If you do not ask for a name, rows arrive labelled by their id and you approve them on whatever you did ask for. Ask for nothing at all and a request carries nothing but that id.
Waiting for approval
Somebody opened the display page on their own device and filled in the form above. Nothing they said is proof of anything — it is what they told you — but a request that arrives saying Sarah, building 4 laptop is one you can act on, where an anonymous row is one you can only guess at. APPROVE grants access and, in the same gesture, whichever endpoints you tick. REFUSE gives them a message and you a note for whoever comes back to this row in six months, and says whether they may ask again. They leave this list the moment you decide and appear under CONNECTIONS ▸ CONNECTIONS, filed with the other people.
Device enrolment
A screen, from naming it to the moment it works. Name one and you are given a six-character code; the row exists from that moment, so its endpoints can be ticked and its profile chosen before the screen it is for has ever been switched on. A code works once, and the clock on its row is counting down what is left of it — set under SECURITY, where it can also be switched off entirely. If it runs out, REISSUE gives another on the current setting: the row is the PLACE, so its name and every endpoint that names it are kept. The screen takes the code either way: type <this server>/e/CODE into its address bar, or open the display page on it and type the six characters into the box it offers. Case and dashes do not matter — k7qp4m is the same as K7QP-4M. A row leaves this list the moment its code is used and appears under CONNECTIONS ▸ CONNECTIONS, filed with the other devices so a grant to all of them is one tick.

Devices
Everything currently connected to this server. A display is one device — a screen on a wall, a TV, a laptop, somebody's phone — and anything with a browser and a microphone counts. People arrived by asking: they opened the display page and filled in the request form, and you approved them. Devices arrived by code: you named one, and somebody typed its six characters into the screen. Both lists are ordered by what was heard from most recently. last seen is the last time one asked this server anything, so a screen unplugged for a week says so here before anybody notices the wall. Anything that has NOT finished arriving is on the tab it is arriving through — ENROLLMENTS ▸ USER for a person waiting on a decision, ▸ DEVICE for a screen that has not taken its code yet. A row moves here on its own the moment it is working. People on a granted request carry access runs out; devices you issued a code for do not, and never will. WITHDRAW takes access away; the row stays here, no longer working. DELETE goes further and forgets the device entirely.
New embed key NOT CREATED YET
Labels the key here and in the server log. It is never sent to the host page and never seen by anybody using the embed.
Start from
A starting point, not a mode. Pick the one nearest what you want and adjust the two lists below — what is stored is the two lists, and the preset is only remembered so the list reads as something you chose rather than as fourteen ticks.
What it may do
Permission, not furniture. Hiding the TALK button under What it draws does not withdraw the microphone — these are two axes on purpose, and the host may narrow either at runtime but never widen one.
What it draws
Parts, not combinations. Some arrangements are incoherent — a TEXT button with no transcript to toggle — and those are refused here in the same words the server uses, rather than discovered after the key is in somebody's application.
Who may frame it
These become the frame-ancestors this server sends, so a page on any other origin cannot frame it at all — a leaked key is useless anywhere you did not name.
Session
How long one exchanged session lasts before the host's server has to ask for another. The key itself does not expire; this is the window a browser holds.
How a host uses it
A key lets another application's server ask this one for a short-lived session and put the result in an iframe. The key never reaches a browser. 1 their server POSTs the key to /embed/session 2 their page frames /embed?t=… with allow="microphone" 3 optionally narrows it at runtime over postMessage — never widens The one everybody hits: a microphone in an iframe needs allow="microphone" and the host page on HTTPS and the permission granted on their origin. Miss one and it looks broken for reasons that have nothing to do with this server. Worked examples in DOCUMENTATION → Embedding it elsewhere.
