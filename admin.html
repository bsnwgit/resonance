Speaker label

The two labels down the left of the transcript. Either can be a variable instead of a fixed word: {name} — the word you say to reach whichever assistant is answering, so renaming that renames this. Already what the greeting and farewell fields use. {assistant} — what answered, which is its own field on each endpoint. This is the default, and with more than one endpoint it is the only label that can be right: a fixed word attributes every answer to the same name. Each line keeps the name of whoever gave it, so switching endpoints mid-conversation does not rewrite what is already on screen. {user} — whoever is signed in here, and the device where nobody is. Put this in the person. It is the only one that can name a person: every other variable here predates accounts, when the nearest thing to a speaker was the machine they typed at. A laptop somebody signs in on labels their words with their name; a wall screen nobody signs in to falls through to the name below, so one setting is right in both places rather than an admin having to choose which to get wrong. {display} — the name of the device this is being viewed at, and only ever that. Put it in the person and every device attributes the transcript to itself, with no setting per device — including the lines typed by somebody signed in, which is what {user} is for. It resolves to the first of these that exists: the name you gave that row under ACCESS, then ?display= from its URL, then the first thing typed on its request form. So a laptop you approved as Sarah laptop labels her lines with that, and a wall screen named Kitchen labels its own. A person's name as distinct from the device they are at — the same name following somebody from laptop to phone — needs an identity they carry, and does not exist yet. Mix them with ordinary text — {display} shift lead is fine. A variable that resolves to nothing falls back to the default, and one that is not recognised is left standing so a typo is visible rather than silent.

Wake word

Whether a name is needed at all, and how long one lasts. The words themselves live on the routes, in AI — with several routes the word is what picks between them, so it belongs to the thing it picks.
The word that reaches an endpoint using this profile, the spellings a transcriber actually returns for it, and how close a match has to be. EXACT is for a profile whose endpoint DOES things rather than answers — the same false-positive rate costs a few tokens on one and actuates hardware on the other.
The fallback for every route that has no greeting of its own. Several lines so a display somebody talks to all day does not repeat itself; {name} is the word that was said to reach whoever answered.

Speech in (mic, STT)

Everything here runs on this server — no audio leaves the box for transcription, whichever model is chosen. transcription model is grouped: the .en models are English-only, smaller and better at English than the multilingual model of the same size; picking one from every language is the only thing that makes this transcribe anything else. Sizes run from ~40MB to ~1.6GB and each option says what it costs, so the list assumes nothing about the machine you are running on. A bigger box wants large-v3-turbo; a modest one wants distil-small.en or the default small.en. A model not already on disk is downloaded the first time somebody speaks after you pick it — inside that request, up to 1.6GB, from a machine that may have no route out. Switch when nobody is waiting at a display, then say something to it yourself to pay for the download. The smaller the model, the more often a wake word is mis-heard — and an assistant set to THE EXACT WORD refuses a near-miss outright, where a CLOSE ENOUGH one forgives it. If you want a fast model on a strict assistant, press LEARN HOW I SAY IT on that assistant and it will accept the spellings this model actually returns. CLEAN filters the input for recognition; RAW leaves it alone, so the figure moves more and transcription is slightly worse. CALIBRATE measures the room rather than asking you to guess at the gate.

Admin settings

Admin Portal

The port is this page's, and only this page's. What the app answers on is a network profile — PROFILES ▸ NETWORK — because a deployment can want several, and which endpoints each carries is a question about the app rather than about the portal. This one stays here on purpose: it is the way back in when what is over there is wrong. 1024–65535, and not a port a network profile or enrolment is using. Below 1024 needs root, and the server runs as an ordinary user. Reachable at is the whole server's, not just this page's — a network profile cannot reach further than what is set here, so binding one address rather than every interface is worth doing on its own account: a laptop that later joins another network does not follow you onto it. This machine only needs no certificate — browsers already treat http://localhost as a secure origin, so the microphone works unprompted and nothing crosses a network. Start it, open localhost, talk to it.

Enrolment

Where an invitation is accepted, and the only place it can be. A link you hand somebody opens here and nowhere else: the same link on any other port of this server answers 404, so somebody who knows a working address cannot substitute it for the one you chose. Nothing else is on this port. No assistant, no microphone, no device enrolment — a browser that opens an invitation must not come away holding a display token. What it answers is the link, the page that asks for a password, and that password being set. Once it is set, the page hands over the addresses of the assistants that person was granted, because this port is not one of them. Interface is which of this machine's addresses it answers on, the same choice a network profile makes. Leaving it on every address is fine; naming one is how you keep enrolment off a network it has no business being on. Address in the link is optional, and it is a name rather than a second binding — the listener answers on the interface above whatever this says. Set it and the link reads https://join.example.com:9703/… instead of four numbers nobody checks. It has to resolve to the interface above, and the certificate has to carry it or every browser will complain: run ./make-cert.sh <name> and restart. Changing the port or the interface needs a restart. The name does not — it is read when a link is minted.

Enrollment Request Form

What somebody is asked when they request access from a display. Up to five fields, and they are yours — this server has no opinion about what a request should ask. Somebody running a campus wants a name and a department; somebody running a house wants none of it. Tick message on one field to make it a box big enough for a reason, and mark the ones that must be answered. If you do not ask for a name, rows arrive labelled by their id and you approve them on whatever you did ask for. Ask for nothing at all and a request carries nothing but that id. The requests themselves are under ENROLLMENTS ▸ USER, in Waiting for approval.

Email

The mail server this one sends through. Nothing here turns anything on: it is the connection, and two things use it. A person's enrolment link. Creating somebody under ENROLLMENTS ▸ USER, or reissuing their link, mails it to the address on their row — so you are not copying a one-time link out of the panel and into a chat window. The link is still shown here once whatever happens, because mail is the convenience and the visible link is the guarantee: a server that hid it because it believed it had sent one would be a server you cannot enrol anybody from the day the SMTP host changes. Alerts, if you switch them on under SETTINGS ▸ ALERT. That is a separate decision — wanting the link mailed and wanting to be paged about a screen going quiet are not the same thing. Leave the server blank and nothing is mailed, anywhere. Everything still works; you hand the link over yourself.

Maintenance

What keeps a screen nobody touches working. Every display checks in on the interval below. That check-in is what keeps LAST SEEN honest in DEVICES, what lets RELOAD there reach a screen, and what lets a screen notice on its own that the server has come back — without it, an outage would end and the screen would stay broken until somebody walked up and spoke to it. A display that has run out of attempts shows a line high on the screen, which clears itself when the server answers again. A kiosk also says it aloud, once — it has no transcript and nobody sitting at it. Nothing else speaks: a screen with somebody in front of it fails at the moment they actually use it, rather than making them wait out the retries. These take effect at each display's next check-in. No restart.
2–300, 1–10 and 1–60. Three attempts is right for a server being restarted and wrong for a cable somebody pulled out, which is why it is a field rather than a constant. Anything outside a range is nudged back into it rather than refused.
Every display reloads itself once a night, because a tab that never reloads accumulates. Off by default. Read off each device's own clock, not this server's, for the same reason a screensaver's dark hours are: a screen's night is the night outside it. And deferred while somebody is talking to the screen or typing into it — a reload that lands between a question and its answer looks like a crash to whoever asked. Spread it if the building has more than a handful of screens: twelve tablets reconnecting in the same second is a load this server did not previously have. Each screen takes its own fixed slot inside the window, so the spread stays put instead of re-shuffling every night.
The server itself, once a day. Off by default. Read off this machine's clock, not a device's — this one is about one server rather than twelve screens. It hands over rather than stopping: at the appointed minute the server launches serve.sh restart in a session of its own and lets that script kill it and start a fresh process. Nothing supervises this server, so a setting that merely stopped it would be a setting that ended the service at three in the morning. The one risk worth knowing. If the new process cannot bind — something else took the port while it was down — nothing catches that, and the server stays down until somebody looks. It is logged to restart.log, which survives the handover where server.log does not. It waits for the server to fall quiet: no question, transcription or spoken reply for a minute. If it never falls quiet it gives up after an hour and leaves it for tomorrow, rather than cutting somebody off mid-sentence. Every display sees this as a short outage and reloads itself when the server answers again — so if you set this, you rarely also need the nightly refresh above.
Users
Everybody who has finished arriving: they opened the link you handed them, chose a password, and sign in with their email address from then on. A person is not a device. A device is one screen standing in one room; a person moves between a phone, a laptop and a borrowed browser and is the same person in all three, which is why their account is something they KNOW rather than a URL sitting in one browser's cookie jar. They start on ENROLLMENTS ▸ USER, where you name one and are handed their link, and they appear here the moment they use it. Nothing is filed by hand and nothing is in both places. REISSUE is the whole of account recovery, and it is deliberately the same gesture as creating somebody: a forgotten password and a leaked link want the same answer. It mints a new link, clears the old password, and signs out every browser they had open. An admin never sets or sees a password — one you chose would be one you knew. Deleting takes everything granted to them with it. What they are granted is on the endpoint under CONNECTIONS ▸ AI, in the People box.

Security

AI Requires Permission

YES — they get the request form instead of the transcript and composer, and reach nothing until you decide. NO — they open the page and use the default endpoint straight away. Restricted endpoints still need a code you issued. Only settable while an endpoint open to any display is the default, or NO would mean access to nothing.
A granted request runs out and the person asks again — one press for them, because what they told you is kept. Displays you issued a code for never expire, whatever this says: a screen on a wall going dark on a timer is not a security property, it is an outage. When more than the waiting limit are queued, the oldest one waiting is dropped to make room — so set it high enough that a real request cannot be pushed out by noise.

Enrolment codes

How long a code is worth anything for after you press GET A CODE. Ten minutes by default, because the usual case is somebody walking across a building with six characters in their head — and the clock beside each one under ENROLLMENTS ▸ DEVICE is counting this down. Zero switches the clock off, and that is a real answer rather than a way of being careless: a code is one use, and the row it enrols was approved the moment you created it. A deployment that mints codes on Friday and hangs the screens on Monday is not less safe for it — what a code can do is become one screen you already decided to have. The clock applies from the moment a code is issued, so changing this does not extend one already out there. REISSUE gives that row a fresh one on the new setting.

Sessions

Idle minutes before an admin has to sign in again. Activity pushes the deadline out; the panel checks every 45 seconds and returns you to the sign-in as soon as it lapses. Short by default — this session configures what everyone else is looking at. 5 to 480. Full reasoning in DOCUMENTATION → App settings & accounts.
Groups
Two populations, and a group holds one of them. USERS holds the people you created under ENROLLMENTS ▸ USER. A person reaches an endpoint from whatever machine they open their URL on, so a grant here follows the human rather than the hardware. DEVICES holds displays — every screen and every laptop, however it got here. Whether it was created here and given a code or turned up and asked is written on the row itself; it does not decide which groups the row may be in, so a group holding a wall screen and somebody's laptop is a perfectly good group. The two cannot mix, and the reason is concrete rather than tidy: they are different files, their ids are minted independently, and a group's kind cannot change once it exists — a kind that changed would not filter the members, it would fail to find any of them. Name a group under an endpoint's who may use it and everyone in it may reach that endpoint. Grants add up: a group never takes away a grant made to one device on its own, and somebody whose access has run out is still refused whatever group they are in. Deleting a group removes it from every endpoint that named it. The devices and people in it are untouched — a group is a way of referring to them, not a thing they belong to.
Appearance profiles
This tab is a workbench, not a document. Nothing you set here reaches a screen on its own: you tune it against the preview and then capture it under a name, and a display shows the profiles it NAMES. A screen in a hallway is read from three metres. A laptop is read from fifty centimetres. One type size cannot be right for both, and neither can one layout: a wall wants the figure filling the frame, a desk wants room for the transcript beside it. That is why these are named rather than shared. There is no default and nothing is inherited. A device naming no appearance profile shows what the page itself ships with — a working screen that nobody has dressed. Deleting a profile puts every device that named it there too. Which profile a device names is set on DISPLAYS, one picker each for appearance, geometry and speech, and NONE is a real answer. PREVIEW lays a profile over the preview on the right without saving it, and follows the controls as you change them. Pressing STOP — or touching anything on APPEARANCE, GEOMETRY or SPEECH — puts the workbench back. Type size tops out at LARGEST, which is the range the APPEARANCE tab offers. If that turns out not to be enough on a real wall, the range is the thing to change, not this.
Geometry profiles
A snapshot of the GEOMETRY tab under a name. Set the rotation, the spectrum and the noise floor up there, watch the preview, then ADD A PROFILE to capture exactly what you are looking at. LOAD puts a profile back into the tab so you can see it and change it; UPDATE replaces it with whatever the tab says now. Loading does not publish anything — the tab is dirty afterwards exactly as if you had moved the controls by hand.
Speech profiles
A snapshot of the SPEECH tab under a name — the voice, the transcription model, the wake and sleep words, the microphone handling. A hallway that has to hear over a corridor and a quiet office want different microphone settings and the same everything else. LOAD puts a profile back into the tab; UPDATE replaces it with what the tab says now.
Model profiles
Where the connection lives: which provider, which base URL, which model, and the key for it. An endpoint on the AI tab picks one. The key never comes back to this page. It is stored on the server and the panel is told only whether there is one — so a profile shows key stored rather than the key, and saving without typing one keeps what is already there. DEMO needs nothing else: the display answers from built-in replies, which is how you tell a fault in the interface from a fault in whatever it is pointed at.
Network profiles
A port of this server's own, answering as one endpoint and nothing else. An endpoint on the AI tab picks one; an endpoint that picks none is reached on the display port, as they all were before this existed. What a browser opening that port gets is the ordinary interface built from that endpoint's own settings — its speech profile, its greeting, its voice — with no other endpoint offered and nothing to address by name. A profile is a port and an address, and nothing about permission. It carried two permission switches once — one letting a port take more than one endpoint, one making the port itself the grant — and both are gone. Who may use an assistant, and whether they have to sign in first, is said on the assistant, under CONNECTIONS ▸ AI. TLS is the same certificate the display port uses, because the microphone needs a secure context and a second certificate for the same machine would be one more thing to renew. Ports are bound when the server starts. Adding a profile, changing a port or pointing a different endpoint at one takes a restart, exactly as the ports on ADMIN do — a listening socket is not something to open and close under a mouse.
Screensaver profiles
A screen showing the same bright figure in the same place for years keeps a ghost of it permanently. A profile is the answer to that, and it is still the product: the same face, every appearance setting still applied, scaled down and drifting. Set them here, pick them on a device. A hallway, a bedroom, a shop floor — that is a handful of kinds of place, not one setting per screen. Change night once and every screen using it changes together; the alternative is twelve rows quietly drifting out of step with no way to see which had. Idle seconds is how long with nobody speaking to it and nobody touching it. 0 never starts, which is how you park a profile without deleting it and unpicking every device that names it. Shrinks to is what makes the drift possible at all: drawn edge to edge there is nowhere to go, and moving it would only clip the sides. The travel is exactly the margin the shrink buys, so nothing is ever cut off. Dims by does more against a ghost than the movement does, and is independently what a hallway should do at two in the morning. It stops short of switching the screen off — you can still see across a room that it is working. PREVIEW tries a profile in the preview on the right without saving it. Nobody picks a scale and a dim by reading two numbers. It ends on the wake word or on a touch, easing back to the middle rather than snapping, and it never starts while an answer is being thought about or spoken. The transcript, the composer and the status line hide while it drifts, and come back the instant the screen is touched. Dark from / until is a different question from the idle delay, and the reason it exists: idle asks whether anybody has been here recently, and only a clock keeps a hallway dark after somebody walks past it at three in the morning. Set the two hours the same and there is no dark window. A start later than an end wraps midnight, which is the ordinary case — 22:00 to 07:00 is what you mean. The two dims never add up. Whichever is darker at that moment wins, so a screen already drifting at night does not go past black. The hours are read off the device's own clock, not this server's. A building with screens in two time zones wants each of them dark at its own two in the morning. Deleting a profile clears it from every device that named it, the same way deleting a display clears it from every endpoint. Nothing keeps drifting to numbers that are no longer here. On a device, in DEVICES, tick Display mode and pick which of these profiles it is. Untick it and the screen goes back to being an ordinary page; what you chose is kept, so putting it back up restores it. A wall is voice only and speak only the moment you tick it. No text box — voice only arrives already ticked, and you untick it for the case that wants a transcript. And no keyboard: push-to-talk holds the SPACE bar, which a tablet on a wall does not have, so a wall always listens and the SPACE button is removed from that screen. That is also what makes the wake word real, because the gate is inactive in push-to-talk. TEXT and SPACE are removed rather than left there refusing. TALK and AUDIO stay — a browser will not open a microphone unless somebody asks it to, so TALK is pressed once when the screen is commissioned. It goes full screen on the first touch. An address bar and a tab strip across the top of a hallway screen is a browser that happens to be running a display. No page can remove that chrome, but it can ask to be shown full screen, and a browser grants that off a gesture — which is why a touch and not a load. Press Escape and it stays out for a minute, because whoever left full screen is nearly always the person installing the screen. It says what to say to it. A wall carries one dim line low in the frame — say “kitchen”, in whatever the wake words are — for the person walking past who has no way of knowing it listens. Never on a browser tab, and not while somebody is talking to it. While the screensaver drifts it is drawn into the picture and travels with it, because taking it away would lose it for exactly the person it is for. It keeps the screen awake. A tablet that has let its backlight go out cannot be walked up to and spoken to: the microphone is behind a page nobody can see. Untick it on a television, or on a device whose operating system is already set never to sleep, where holding the lock gains nothing. When a device takes a change. Every display checks in on the interval under APP SETTINGS ▸ MAINTENANCE, and reloads itself when something it draws from changes — so an appearance or a profile edited here reaches the wall without anybody walking to it. Never while somebody is talking to the screen or typing into it: it waits until they have finished. RELOAD on a device's row in DEVICES asks one directly.
Display profiles
A kiosk is a screen people walk up to, that nobody has open and nobody is sitting at — a wall, a stand, a reception counter, a tabletop. The mounting was never what any of this followed from: what it follows from is that nobody owns the session and nobody has a keyboard. Build them here, pick one on a device. A hallway, a reception desk, a shop floor — a handful of kinds of place, not one setting per screen. Change what a hallway does once and every hallway screen changes with it. Voice only takes away the transcript and the composer, and it outranks what the viewer chose: a hallway is not a workstation, and a screen of scrolling text in one is neither useful nor discreet. Full screen is asked for on the first touch. Turn it off where somebody also browses on that machine, or where the operating system already hides the chrome. The prompt line is one dim line low in the frame telling a passer-by this listens. Leave the text empty and it writes itself from the wake words the screen actually answers to — which stays right when you rename one. Type something only where the generated line is not the point. The default is what a device gets when it names no profile, and you choose which one that is. A screen hung on a wall and never configured behaves like the rest of the building rather than like nothing.
People
A person, as against a device. A device is one screen standing in one room; a person moves between a phone, a laptop and a borrowed browser and is the same person in all three. Name them, give them an address, tick their assistants, hand over the link. The address is what they will sign in with; the link is what lets them choose a password, and it buys exactly that one thing. The ticks are the grant, and the same grant each endpoint's own Who may use it list makes. Tick none and they reach whatever is open to everyone; an endpoint that is open to everyone is reachable already, so ticking it grants nothing. They can be changed afterwards on the person's own row, or from the endpoint. The link always opens in one place — the enrolment listener, under SETTINGS ▸ ADMIN ▸ Enrolment. The same link on any other port of this server answers 404, so somebody who knows a working address cannot substitute it. Once they have chosen a password, that page hands them the addresses of the assistants you ticked, because the enrolment port is deliberately not one of them. It is shown once, here, at the moment you create it — what is stored is a hash, so this page cannot show it to you a second time. Hand it over before you leave the row. You never see their password and cannot set one. They choose it from the link, and an admin who chose it would know it. That is the whole reason the link exists rather than a password field on this row. A row leaves this list the moment they use it, and appears under IDENTITY ▸ USER — the same move a screen makes from ENROLLMENTS ▸ DEVICE to NODES when it takes its code. This list is the ones who have not turned up yet. NEW LINK replaces an outstanding one; on somebody who is already here it is called REISSUE THE LINK, and it is the whole of account recovery — a new link, the old password cleared, every browser they were signed in on signed out. A forgotten password and a leaked link want the same answer. A link will not work on a screen you approved. A device is a device, and turning a shared kiosk into somebody's personal session is the case it is least for. The link is not spent by being refused there.
Waiting for approval
Somebody opened the display page on their own device and filled in the form above. Nothing they said is proof of anything — it is what they told you — but a request that arrives saying Sarah, building 4 laptop is one you can act on, where an anonymous row is one you can only guess at. APPROVE grants access and, in the same gesture, whichever endpoints you tick. REFUSE gives them a message and you a note for whoever comes back to this row in six months, and says whether they may ask again. They leave this list the moment you decide and appear under CONNECTIONS ▸ NODES, in the one register with every other device, badged ASKED for the door they came through.
Device enrolment
A screen, from naming it to the moment it works. Name one and you are given a six-character code; the row exists from that moment, so its endpoints can be ticked and its profile chosen before the screen it is for has ever been switched on. It is not approved until the code is used. Naming a screen is an invitation, not a device — the row holds a code and nothing else, so until somebody carries that code to the television it is not offered as a member of a group and does not count as a display that works. Reissuing a code puts it back to exactly that state. A code works once, and the clock on its row is counting down what is left of it — set under SECURITY, where it can also be switched off entirely. If it runs out, REISSUE gives another on the current setting: the row is the PLACE, so its name and every endpoint that names it are kept. The screen takes the code either way: type <this server>/e/CODE into its address bar, or open the display page on it and type the six characters into the box it offers. Case and dashes do not matter — k7qp4m is the same as K7QP-4M. A row leaves this list the moment its code is used and appears under CONNECTIONS ▸ NODES, in the one register with every other device, so a grant to all of them is one tick.
Nodes
Display mode assignment nothing selected
Everything currently connected to this server. A display is one device — a screen on a wall, a TV, a laptop, somebody's phone — and anything with a browser and a microphone counts. Every one of them is in one list, and how it arrived is on the row rather than over it. ASKED is a device whose user opened the display page, filled in the request form and was approved; INVITED is one you named and somebody typed the six characters into. Two doors into the same building: once a laptop that asked and a wall screen you issued a code for are both in, they are the same kind of thing, and finding one of them used to mean first remembering which of two lists it had been filed under. The list is ordered by what was heard from most recently. last seen is the last time one asked this server anything, so a screen unplugged for a week says so here before anybody notices the wall. Anything that has NOT finished arriving is on the tab it is arriving through — ENROLLMENTS ▸ USER for a person waiting on a decision, ▸ DEVICE for a screen that has not taken its code yet. A row moves here on its own the moment it is working. A device on a granted request carries access runs out; one you issued a code for does not, and never will. WITHDRAW takes access away; the row stays here, no longer working. DELETE goes further and forgets the device entirely.
Health
What was said to them
A screen with a fault cannot tell anybody. This is where it says so: a microphone that would not open, a browser with no recorder at all, transcription running long, the neural voice quietly falling back to the browser's, and the wake word it actually matched on. Most of this was already worked out and thrown away. The display says woke on “hows” (near “house”) as a note that fades — which on a wall nobody is ever there to read. Kept here, it is also the only way to find out that two wake words are cross-triggering. CLEAR on a row forgets what one screen reported without taking it off the wall — for a fault that has been fixed.
Alerts
An alert has four states, not two: open or resolved, acknowledged or not. The one that matters is resolved but unread — a screen that dropped off at two in the morning and came back four minutes later leaves something here until a person sees it. Self-healing nobody ever hears about is indistinguishable from nothing having happened, and a display that heals itself every night is a fault rather than a success. Resolving is automatic; acknowledging is not. A screen that comes back resolves its own alert, and it stays in this list until you press the button. Anything both resolved and acknowledged has nothing left to say and leaves. One of these depends on nothing else here: a device asking to be let in arrives the moment it asks, because it is the only alert with a person attached to it — somebody is standing at a screen waiting.

them who is now signed in. Neither is a thing to switch on for somebody.

One per line. Several lines and it picks one, the same as the greeting
phrases — a screen somebody signs into all day should not say the same words
every time. {name} and the other variables work here too.

It needs the local voice to be reliable. A browser will only start
speech synthesis inside the gesture that asked for it, and whether a sign-in
worked is not known until the server has answered — by which time that gesture
has been spent. The local engine plays audio instead and is not subject to
that, so on SPEECH ▸ engine LOCAL this always speaks. On the browser
voice it may be dropped silently; nothing else breaks.

    

  


  

    
Alerts

    

  

    
  

  
  

    
      
      
    
    
      
      
    
    
      
      
    
    
      
      
    
    
  

  

    
  

  

    
      
      
    
  

  

    
  

  

    
      
      
    
    
      
      
    
    
      
      
    
  

  
  

    
  

  

    
      
      
    
  

  

    
  

  

    
    
  

  

    
  

  

    
    
    
    
  

  

  
Cheapest reach after this list, by a distance: the
standard library speaks it, every operator already has somewhere it goes, and
it costs one socket and no credentials.

Sent when an alert opens and again when it resolves — a screen that came
back at four in the morning is exactly what somebody reading a log at nine
wants to see beside the line saying it went. Severity follows the alert:
errors as err, warnings as warning, recoveries as info.

Fire and forget. Nothing here retries or blocks, because a sink that did
would turn reporting a fault into a second fault — and the alert it failed to
send is still in the list above, which is why that one is not optional.

Where the mail server is set: SETTINGS ▸ ADMIN ▸ Email. It is one
connection, shared — the same one sends somebody their enrolment link — so it
is not configured here. With no server set there, ticking this sends nothing.

Source name is what the collector files these lines under. Blank uses
this machine's own hostname, which is what a collector would infer from the
packet anyway — the field is for when that is not the name you want to read: a
host called srv-04b answering for the thing everybody calls the kitchen,
or several installs arriving behind one address.

It applies to a remote collector only. Sending to the local daemon
leaves the header to the daemon, which is already writing one; a second would
put the name inside the message text instead of in the column. Spaces become
hyphens, because the format ends that field at the first space.

The format carries no time zone — the timestamp is local time with
nothing marking it as such, so a collector in another zone reads it as its
own. That is RFC 3164 rather than a choice made here, and the alternative is a
line some parsers reject outright.

A webhook is one JSON POST and reaches ntfy, Slack, Discord, Gotify and
whatever else you already run — the most reach per line of code available here,
because they all take a body with a message in it.

Home Assistant is the strongest one here, because it can speak: a screen
that dies gets announced by the building it is part of. It has its own
connection rather than borrowing an endpoint's — alerting that hung off a
route would disappear the day somebody deleted that route, which is a
surprising way to lose the thing that tells you a screen is dead.

persistent_notification.create is the default because it always exists
and needs nothing configured. notify.notify, or a tts service, is the one
that actually speaks. The token is stored here and never sent back to this page;
leaving the field blank keeps the one already saved.

Quiet hours run on this machine's clock, the same one dark hours use,
and they span midnight the way a night does: 22 until 7 is a night, not
nineteen hours of daylight. Nothing is dropped — it is held, and the list still
has it. Announcing a dead hallway screen through the house speakers at three in
the morning is how alerting gets switched off in its first week.

Two exceptions, both deliberate. Syslog ignores quiet hours, because a
log with a hole in it every night is useless for the one fault that only
happens at night. And a device asking to be let in comes through anyway —
somebody is standing at a screen waiting, whatever time it is.

Email is last on this list and that is not an accident. It costs no
dependency, but it wants a server and credentials and it fails somewhere this
process cannot see more often than anything else here. The password is stored
and never sent back to this page; blank keeps the one saved.

A digest gathers everything held and sends it as one message, timed from
the OLDEST thing waiting rather than from the last digest — what matters is how
long something has gone unsaid, not how long since a message that may have
carried nothing. It is also what makes quiet hours a hold rather than a drop:
nothing goes out during the quiet, and it all arrives afterwards. A device
asking to be let in ignores this too.

    

  


  

    
Server log

    

  

    
    
    
  

  

  
How much of the log STATUS answers with. It bounds the
ANSWER and not the read: the server always seeks the last 256KB off the end of
the file, so asking for more lines cannot turn opening a page into the thing
that makes the server slow — and asking for fewer does not make it faster.

Worth turning down where a building of screens checks in every twenty seconds
and the interesting line is always the last one; worth turning up on a house
with three, where the whole file is worth reading.

    

  


  

    
Health

    

  

    
    
    
  

  

  
Retention is the control, and it is short on purpose. This holds what
was addressed to a screen, so a generous default would be a decision made on
somebody's behalf about their household. Nothing outside a conversation is
recorded, and nothing at all until somebody says a wake word.

Start from

    

  

    
    
    
    
    
    
  

  
A starting point, not a mode. Pick the one nearest
what you want and adjust the two lists below — what is stored is the two
lists, and the preset is only remembered so the list reads as something you
chose rather than as fourteen ticks.

    

  


  

    
What it may do

    

  

    
    
    
  

  
Permission, not furniture. Hiding the TALK button
under What it draws does not withdraw the microphone — these are two
axes on purpose, and the host may narrow either at runtime but never widen
one.

    

  


  

    
What it draws

    

  

    
    
    
    
    
    
    
  

  
Parts, not combinations. Some arrangements are
incoherent — a TEXT button with no transcript to toggle — and those are
refused here in the same words the server uses, rather than discovered after
the key is in somebody's application.

    

  


  

    
Who may frame it

    

  
  
  
These become the frame-ancestors this server
sends, so a page on any other origin cannot frame it at all — a leaked key is
useless anywhere you did not name.

    

  


  

    
Session

    

  
  
  
How long one exchanged session lasts before the host's
server has to ask for another. The key itself does not expire; this is the
window a browser holds.

    

  


  

    
How a host uses it

    

  
A key lets another application's server ask
this one for a short-lived session and put the result in an iframe. The key
never reaches a browser.

1 their server POSTs the key to /embed/session
2 their page frames /embed?t=… with allow="microphone"
3 optionally narrows it at runtime over postMessage — never widens

The one everybody hits: a microphone in an iframe needs
allow="microphone" and the host page on HTTPS and the permission
granted on their origin. Miss one and it looks broken for reasons that have
nothing to do with this server.
